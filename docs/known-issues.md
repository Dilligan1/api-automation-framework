# Известные дефекты тестируемой системы

Дефекты, найденные автотестами и воспроизведённые вручную. Тест на дефект
не удаляется и не ослабляется — он помечается `xfail` со ссылкой на этот
документ, чтобы после исправления бага прогон сам об этом сообщил.

---

## BUG-001 — 500 при выдаче двух одинаковых токенов в пределах одной секунды

| | |
|---|---|
| **Severity** | Major |
| **Компонент** | Auth |
| **Найден** | `tests/smoke/test_auth.py::TestAuthSmoke::test_refresh_issues_new_pair` (refresh) и параллельный прогон `pytest -n 4` (login) |
| **Статус** | Открыт |

### Шаги воспроизведения

Дефект проявляется двумя способами.

**A. Обновление токена сразу после входа**

1. `POST /api/auth/login` — получить пару токенов.
2. Немедленно (в пределах той же секунды) вызвать `POST /api/auth/refresh`
   с полученным `refresh_token`.

**B. Конкурентный вход одного пользователя**

1. Выполнить несколько `POST /api/auth/login` одного пользователя одновременно.

```
4 одновременных логина одного пользователя -> [500, 200, 200, 500]
```

### Фактический результат

`HTTP 500 Internal Server Error`, тело — `Internal Server Error`.

В логах бэкенда:

```
sqlalchemy.exc.IntegrityError: UniqueViolationError:
duplicate key value violates unique constraint "refresh_tokens_token_hash_key"
DETAIL: Key (token_hash)=(7de1430b…) already exists.
[SQL: INSERT INTO refresh_tokens (id, user_id, token_hash, expires_at, ...)]
```

### Ожидаемый результат

`HTTP 200 OK` с новой парой токенов.

### Причина

Полезная нагрузка JWT содержит `iat`/`exp` с точностью до секунды. Если
refresh вызван в ту же секунду, что и выдача токена, сервис генерирует
**побайтово идентичный** refresh-токен и пытается вставить его хэш в
`refresh_tokens`, где на `token_hash` стоит UNIQUE. Нарушение ограничения
не обрабатывается и всплывает как 500.

### Подтверждение зависимости от времени

```
login                          -> 200
refresh сразу                  -> 500
refresh через 2 с после логина -> 200
```

### Влияние

Воспроизводится у любого клиента, который обновляет токен сразу после входа
(мобильное приложение с коротким TTL access-токена, автотесты), а также при
одновременном входе одного пользователя с нескольких устройств. Пользователь
получает 500 вместо сессии.

Практическое следствие для автотестов: пользователи должны быть разведены
между сценариями, которые логинятся явно, и фикстурами `TokenProvider`.
Именно поэтому `test_login_returns_token_pair` работает с пользователем
LONGREAD — под ним не логинится ни одна фикстура.

### Как это исправить

Добавить в payload токена уникальный `jti`, либо обрабатывать
`IntegrityError` и возвращать существующий валидный токен.

### Обходной путь в тестах

Тест помечен `xfail` (нестрогий: при разнесении вызовов по секундам он
проходит). После исправления дефекта — снять маркер.
