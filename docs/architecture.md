# Архитектура фреймворка

## Принцип

Тест не знает ни про HTTP, ни про URL, ни про заголовки. Он оперирует бизнес-действиями:
`post_api.create(payload)` — и проверяет уже типизированный объект. Всё, что ниже, спрятано за слоями.

```
        тест (tests/)
            │  бизнес-действие + assert
            ▼
   сервис (services/<domain>/api.py)
            │  payload → метод → Pydantic-модель
            ▼
   APIHelper (utils/api_helper.py)
            │  проверка статуса, десериализация, Allure
            ▼
   HTTPClient (utils/http_client.py)
            │  requests.Session, retry, логирование
            ▼
          SUT
```

## Слои и их границы

### `utils/http_client.py` — транспорт
Единственное место, где вызывается `requests`. Держит одну сессию на весь прогон (keep-alive), настраивает retry на 429/502/503/504 и прикрепляет URL и тело запроса в Allure. Ничего не знает про домены и модели.

### `utils/api_helper.py` — валидация
База всех сервисных классов. Делает три вещи: прикрепляет ответ в отчёт, сверяет статус-код, десериализует тело в Pydantic-модель. Флаг `success=False` переключает метод в режим негативной проверки — тот же метод сервиса переиспользуется без дублирования.

### `services/<domain>/` — доменный слой
Каждый домен разложен на четыре файла:

| Файл | Ответственность |
|---|---|
| `endpoints.py` | URL, собранные из `config.stages.API_PREFIX`. Пути с параметрами — `@staticmethod` |
| `payloads.py` | Pydantic-модели запросов. Имена полей совпадают с API намеренно |
| `models/responses.py` | Pydantic-модели ответов |
| `api.py` | Методы сервиса. Каждый — под `@allure.step`, возвращает модель |

Модели, общие для нескольких доменов (`PaginatedResponse`, `UserBrief`, `PostResponse`), вынесены в `services/common/` — бэкенд отдаёт их из разных сервисов, дублировать схему нельзя.

### `auth/token_provider.py` — авторизация
Пользователи описаны `Enum`, учётные данные берутся из `.env` по префиксу. Токен кэшируется дважды: в памяти процесса и в файле под `FileLock`. Второй уровень нужен для `pytest-xdist`: без него каждый worker логинился бы независимо, создавая лишнюю нагрузку и гонки сессий. Файловый кэш очищает мастер-процесс в `pytest_configure`.

### `config/` — окружение
`stages.py` выбирает хосты по переменной `STAGE`, любой хост переопределяется через env. `test_data.py` хранит seed-пользователей и границы бэкенда (2000 символов, 5 MB, 3 уровня вложенности) — тесты ссылаются на константы, а не на магические числа.

### `utils/db_handler.py` — прямой доступ к БД
Нужен там, где состояние через API не воспроизвести: «состарить» пост, чтобы выйти за 15-минутное окно редактирования, проверить `is_deleted` у soft-deleted записи, сверить денормализованные счётчики. Контекстный менеджер закрывает соединение даже на упавшем тесте.

## Правила, которые держат проект в форме

1. Тест наследуется от `BaseTest` — bare `def test_*()` запрещены.
2. Никаких хардкодов входных данных: только `DataGenerator`.
3. Тест убирает за собой — стенд общий, `reset` в параллельном прогоне вызывать нельзя.
4. Каждый метод сервиса и каждый шаг теста размечен `@allure.step` / `with allure.step`.
5. Ассерты пишутся с сообщением, в котором видно ожидаемое и фактическое значение.
