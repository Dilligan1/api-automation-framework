# Тест-план

## Уровни и их назначение

| Уровень | Маркер | Что проверяет | Когда гоняется |
|---|---|---|---|
| Smoke | `smoke` | Каждый сервис жив, основной метод отвечает и отдаёт валидную схему | На каждый push, до остальных уровней |
| Negative | `negative` | Коды ошибок, границы значений, разграничение прав | На каждый push |
| Regression | `regression` | Широкое покрытие методов и вариаций (позитив, границы, негатив) | Ночью и перед релизом |
| E2E | `e2e` | Сквозной бизнес-путь, один тест на роль | Ночью и перед релизом |

Дополнительные маркеры: `critical` (бизнес-критичные проверки — подмножество любого уровня), `slow` (дольше 10 секунд).

## Что где лежит

### Smoke
Один тест — один метод API. Никаких цепочек: если smoke красный, должно быть сразу видно, какой сервис лёг. Обязательный первый тест прогона — `tests/smoke/test_system.py::test_health_check`.

### Negative
Три группы:
1. **Валидация входа** — пустые и переполненные поля, неверные форматы → 422.
2. **Права доступа** — чужие сущности и админские методы от обычного пользователя → 403; отсутствие токена → 401.
3. **Несуществующие сущности** → 404 (а не 500).

### E2E
Один тест на пользователя, всё внутри одного метода, этапы — `allure.step`. Состояние живёт в локальных переменных: тест самодостаточен и безопасен для параллельного прогона. Общая логика в `tests/e2e/base_flow.py`, привязка к роли — в `tests/e2e/<user>/conftest.py`.

Покрытые роли: `admin`, `user_active`, `user_private` (плюс отдельный флоу подписки на приватный аккаунт), задел — `moderator`, `user_banned`.

## Приоритеты покрытия

| Приоритет | Функциональность | Обоснование |
|---|---|---|
| Blocker | Логин, выдача и обновление токена | Без этого не работает ни один тест и ни один пользователь |
| Blocker | Разграничение прав admin/moderator/user | Дефект здесь — уязвимость, а не баг UX |
| Critical | Создание, чтение, удаление постов | Основной пользовательский сценарий |
| Critical | Подписка на приватный аккаунт (`pending → accepted`) | Самый сложный статусный переход |
| Major | Комментарии, реакции, закладки | Массовые действия, высокая частота использования |
| Major | Загрузка изображений и её лимиты | Работа с файлами, типичная зона дефектов |
| Minor | Поиск и тренды | Отказ деградирует UX, но не блокирует работу |

## Тестовые данные

Seed-набор песочницы фиксирован и восстанавливается `POST /api/reset`. Восемь пользователей покрывают состояния, которые иначе пришлось бы готовить вручную: верифицированный, приватный, без контента, забаненный, модератор, администратор.

Всё, что тест создаёт сам, генерируется `DataGenerator` и удаляется после теста. Правило: **после прогона стенд должен остаться в том же состоянии**, в котором был до него.

## Параллельный прогон

Тесты рассчитаны на `pytest -n <N>`. Условия, которые это обеспечивают:
- токены кэшируются в файле под `FileLock` — пользователь логинится один раз на весь прогон, а не на каждый worker;
- тесты не завязаны на порядок выполнения и не делят изменяемое состояние;
- `POST /api/reset` вызывается только мастер-процессом до старта worker'ов (`RESET_BEFORE_RUN=true`), но никогда из теста.
